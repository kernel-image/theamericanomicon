# THE AMERICANOMICON SPATIAL AUDIO ARCHIVE

## Project Overview
The americanomicon was an experimental music project from the 2000s. 
This web app allows users to explore recordings in 3D listening rooms
built with THREE.js, using PositionalAudio for spatial sound and
AudioAnalyser data to drive TSL shaders via WebGPURenderer,
with an automatic WebGLRenderer fallback (via Three.js `getFallback` callback) when WebGPU is unavailable.

---

## Architecture Summary

### Renderer Strategy
- **Primary:** WebGPURenderer (Three.js r170+) — enables TSL-native shaders, better performance on supported hardware
- **Fallback:** WebGLRenderer — used when WebGPU is unavailable or init fails
- **Automatic fallback via Three.js `getFallback` callback** — Three.js base `Renderer.init()` catches backend init errors and calls the `getFallback` callback. Pass a factory function that returns a WebGLRenderer instance. No manual try/catch boilerplate needed; Three.js handles the switch transparently.
- **Text rendering:** CanvasTexture approach — LLM-generated text is written to an offscreen <canvas> element and used as a THREE.CanvasTexture applied to static surface materials. Works with both WebGPURenderer and WebGLRenderer. No external text library needed.

### Technology Stack
| Layer | Technology | Notes |
|---|---|---|
| Build | Vite 5+ | Native ESM, fast HMR, top-level-await for WASM |
| Language | JavaScript (ESM) | Simpler development; no TypeScript overhead |
| 3D Engine | Three.js r170+ | WebGPURenderer + WebGLRenderer automatic fallback via `getFallback` |
| Shaders | TSL (Three.js Shading Language) | NodeMaterial-based; parity check required for WebGL fallback |
| Text Rendering | CanvasTexture (offscreen <canvas> → THREE.CanvasTexture) | Works with both renderers; no external deps |

| Text Formatting | Prettier + ESLint | Code quality |

### Build System: Vite
- Native ESM support eliminates transpilation overhead for modern Three.js
- Built-in top-level-await (needed for dynamic imports of wllama WebGPU backend)
- Simple configuration for a browser-only JS project
- No need for TypeScript tooling — project uses plain JavaScript

## Room Construction

### Active Walls (Left, Front, Right)
- Three separate PlaneGeometry meshes with subdivision count WALL_RES
- Share a single ShaderMaterial (TSL) that responds to audio frequency data
- UV continuity scheme: each wall occupies one-third of the UV space
  - Left wall:   UV.u = 0.000 - 0.333
  - Front wall:  UV.u = 0.333 - 0.666
  - Right wall:  UV.u = 0.666 - 1.000
  - UV.v = 0.000 - 1.000 for all walls
- This creates a seamless continuous texture across all three walls
- Audio displacement modifies vertex positions along normals

### Static Surfaces (Floor, Ceiling, Back Wall)
- Simple PlaneGeometry meshes (no subdivisions)
- Materials receive dynamic textures generated by text rendering system
- Text content generated by local LLM (wllama) with prompt from track title
- Texture updates throttled (e.g., only periodically when camera is looking at the surface)

### Doors and Doorframes
Each doorway consists of:

1. **Doorframe**: Constructed from three transformed BoxGeometry pieces
   - Left pillar, right pillar, top header
   - Each piece scaled and positioned to form a frame opening
   - Grouped into a single parent Object3D

2. **Portal Trigger**: A flat, dark BoxGeometry occupying the negative space
   - Invisible (transparent) but clickable via Raycaster
   - Acts as the click target for room navigation
   - userData.targetRoom specifies destination room ID

3. **Instancing**: Complete doorframe assemblies (frame + trigger) are:
   - Duplicated with position offsets
   - Batched using InstancedMesh for performance
   - Each room has two doors (left and right rear corners
   on back wall)

---

## Room Navigation
- Two doors per room: right and left rear corners
- Doors are clickable via Raycaster on the portal trigger mesh
- On click: camera lerps toward door position, scene fades to black
- Audio track pauses, progress and generated text saved via EventDispatcher
- New room constructed, playback resumes if state history exists

## Audio Processing

### Sampling Strategy
- AudioAnalyser sampling occurs at a configurable interval, NOT every frame
- `samplingLatency` parameter controls update frequency (e.g., 50ms)
- Reduces CPU load from getByteFrequencyData calls
- Shader receives new data via uniform and smoothly interpolates

### Shader Time Management
- `samplingLatency` passed as uniform to shader
- Shader scales its internal delta time accordingly
- Enables smooth lerp between audio samples regardless of frame rate

### State Management
- Uses EventDispatcher pattern (built into Three.js)
- Tracks: currentRoom, playback progress, generated text history

### Room Manifest (data/roomManifest.json)
```json
{
  "rooms": [
    {
      "id": "room_001",
      "audioAsset": "tracks/song_a.mp3",
      "shaderName": "bassPulse",
      "shaderParams": { "intensity": 0.8, "speed": 1.0 },
      "llmPromptTemplate": "prompts/room_001.txt"
    }
  ]
}
```

### Initial Loading Scene
- Camera falls through a pool of instanced bookshelves with instanced books
- Runs while: rooms copied to app data object and order shuffled, audio preloaded, first room textures generated, adjacent rooms preloaded
- When ready: destroy library scene, start first room's audio

### Camera
- Use THREE.OrbitControls initially

### Toolchain
- Vite build system (not webpack)
- Plain JavaScript (ESM) — no TypeScript
- Canvas2D API for text rendering (no external text library)
- Code style enforced by .prettierrc
- Lint with eslint
- Test with Vitest

### Technical Requirements
- WebGPURenderer primary, WebGLRenderer fallback via Three.js `getFallback` callback (automatic switch on init failure)
- All shaders written in TSL (Three.js Shading Language) — must compile to both WebGPU and WebGL backends
- PositionalAudio with AudioAnalyser for frequency data
- Raycaster for door click detection
- CanvasTexture for dynamic text on static surfaces (no external library)
- wllama for local LLM inference (WebGPU backend preferred, runs in Web Worker)
- COOP/COEP headers: optional — only needed if using wllama's WASM multi-threaded path; not required when using the WebGPU backend

## Directory Structure
```
src/
  main.js              # Entry point, renderer init, app bootstrap
  app/
    scene.js           # Scene setup (library intro + rooms)
    audio/             # Audio system (PositionalAudio, AudioAnalyser)
    rooms/             # Room construction, navigation
    shaders/           # TSL shader definitions
    text/              # CanvasTexture text generation and management
    llm/               # Wllama integration layer
    ui/                # UI overlays, loading screens
  data/                # Application data: roomManifest.json, LLM prompt templates

assets/                # Local dev stubs only (placeholder tracks for testing)
                         # Production media is hosted externally; manifest URLs point to CDN
public/                # Static assets served directly (favicon, etc.)
tests/                 # Test files
```

**Note:** Audio tracks and other media are expected to be hosted on an external server. The root-level `assets/` directory exists only for local development stubs. Prompt templates and the room manifest live in `src/data/` as application configuration, not media assets.

## Project Constraints & Known Risks

### Known Risks
1. **wllama inference latency** — A ~500MB model takes 2-8 seconds to generate text depending on GPU class.
2. **WebGPU mobile support** — WebGPU on iOS Safari is experimental; Android Chrome has partial support. WebGLRenderer fallback must be thoroughly tested on mobile devices.
3. **CanvasTexture resolution** — Text texture size must balance sharpness against GPU memory. Poorly sized canvases can look blurry at distance or waste VRAM. Requires tuning per surface.

### Browser Requirements
- Minimum: Modern browser with WebGL 2 support (Three.js falls back to WebGLRenderer automatically via `getFallback` callback if WebGPU init fails)
- Optimal: Browser with WebGPU support (Chrome 113+, Edge 113+, Firefox Nightly with flag)
- Mobile: Limited support — WebGPU on iOS Safari is experimental; Android Chrome has partial support. WebGL 2 fallback ensures functionality still works.
